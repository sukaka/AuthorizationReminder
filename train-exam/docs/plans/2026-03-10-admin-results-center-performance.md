# 管理员结果中心性能优化方案

## 目标

让管理员结果中心在真实业务场景下做到：

- 打开结果列表时快
- 筛选结果时稳
- 打开卷面详情时只加载真正需要的数据
- 连续查看多份结果时不越来越卡

## 当前基线

这份方案基于代码路径分析，不是浏览器实测。

已确认的当前行为：

1. 打开结果相关入口时，会同时请求多个模块数据
   - `fetchMyResults`
   - `fetchCertificateCenter`
   - `fetchCertificateTemplate`
   - 入口位置：`/Users/zhanglei/Documents/codex-new/train-exam/frontend/src/App.jsx:3833`

2. 结果列表接口是整表返回，不分页
   - 前端：`/Users/zhanglei/Documents/codex-new/train-exam/frontend/src/App.jsx:1245`
   - 后端：`/Users/zhanglei/Documents/codex-new/train-exam/backend/src/index.js:6494`

3. 打开一份历史结果时，前端会串行请求两次
   - 先请求结果详情 `/results/:id`
   - 再请求考试会话 `/exam-sessions/:sessionId`
   - 位置：`/Users/zhanglei/Documents/codex-new/train-exam/frontend/src/App.jsx:2862`

4. 考试会话接口会一次性返回整份试卷所有题目的快照和答案
   - 位置：`/Users/zhanglei/Documents/codex-new/train-exam/backend/src/index.js:6359`

5. 结果详情查看会复用考试页主状态
   - 会写入 `currentSession / currentQuestions / currentResult`
   - 位置：`/Users/zhanglei/Documents/codex-new/train-exam/frontend/src/App.jsx:2875`

## 主要瓶颈

### 1. 初始请求过多，且不区分当前任务

管理员打开“结果”时，系统不区分“我要看考试结果”还是“我要管理证书”，直接把成绩、证书、模板一起拉。

问题：

- 首屏无关请求占带宽
- 结果页打开速度被证书模块拖慢
- 后续管理员结果中心如果继续叠功能，会更重

### 2. 列表接口粒度过粗

`/my/results` 直接返回全部记录，没有分页，也没有“轻量摘要版”和“详细版”的区分。

问题：

- 记录多时首屏越来越慢
- 管理员场景会比个人场景大得多，整表返回不可扩展

### 3. 详情链路是串行双请求

先取结果详情，再取会话题目详情，天然多一次 RTT。

问题：

- 打开卷面详情的等待感明显
- 连续看多份卷面时会反复两跳

### 4. 会话详情返回体过重

会话接口会把每道题的快照、用户答案整包返回。

问题：

- 大试卷 payload 大
- 手机与慢网更明显
- 即使用户只想看顶部摘要，也必须先等整卷回来

### 5. 结果查看和考试作答共用状态容器

历史结果详情塞进考试页状态，属于“重状态复用”。

问题：

- 结果查看触发大量无关状态更新
- 容易导致主组件重渲染范围过大
- 不利于后续按模块做代码拆分

### 6. 单文件大组件不利于按需加载

当前前端主要逻辑集中在一个大 `App.jsx` 中，结果中心没有独立代码边界。

问题：

- 很难做 route-level code split
- 一个区域状态变化，容易带动整页逻辑参与渲染

## 优化目标

建议把管理员结果中心的目标定成：

- 首次打开结果列表：`<= 1` 个核心请求
- 列表接口：默认分页，单页 `20-50` 条
- 打开详情：优先 `1` 个聚合请求，最多 `2` 个并行请求，不再串行
- 详情页首屏：先到“摘要”，题目明细按需展开
- 连续打开 5 份卷面时：不重复加载已看过的数据

## 优化策略

## 一、加载策略优化

### 1. 拆开“考试结果”和“证书中心”

不要在结果页入口同时加载：

- 成绩列表
- 证书中心
- 证书模板

建议：

- 管理员结果中心只先加载结果列表
- 证书相关在用户切到证书模块时再拉
- 证书模板仅在模板维护面板打开时才拉

这是最直接的首屏减负。

### 2. 管理员结果列表使用轻量摘要接口

新增管理员结果列表 API，不返回整份 `detail_json`，只返回列表必要字段：

- result_id
- user_id
- username
- department
- paper_id
- paper_name
- score
- total_score
- passed
- attempt_no
- is_final
- created_at
- duration_seconds
- wrong_count

不要在列表里返回：

- 全量题目明细
- AI 建议全文
- 大块 JSON

### 3. 详情改成聚合接口

现状是：

- `/results/:id`
- `/exam-sessions/:sessionId`

建议改成管理员详情专用接口，例如：

- `/results/:id/review-detail`

一次返回：

- 顶部结果摘要
- 题型统计
- 题目列表基础数据

如果题目明细很多，再拆第二级：

- 详情页首屏先返回题目概要
- 展开某题时再加载解析或长文本

## 二、网络与数据优化

### 4. 列表必须分页

管理员结果中心不能沿用整表返回。

建议：

- 默认每页 `20`
- 支持 `20 / 50 / 100`
- 后端返回：
  - `items`
  - `total`
  - `page`
  - `limit`
  - `total_pages`

### 5. 增加筛选摘要接口或并入列表响应

管理员会频繁改筛选，顶部摘要如果独立请求太多，会让页面显得碎。

建议：

- 把 `总考试数 / 通过率 / 平均分 / 异常数` 放到列表接口同响应里
- 或做一个轻量 summary 接口，与列表并行加载

但不要每个摘要单独一个请求。

### 6. 增加前端结果详情缓存

管理员经常：

- 打开详情
- 返回列表
- 再次打开同一条

建议：

- 用 `resultId` 做本地缓存
- 缓存结果摘要和卷面详情
- 过滤条件变化时只清理列表缓存，不清掉已打开的详情缓存

### 7. 避免重复刷新整个结果集合

当前很多动作完成后都会再次整批拉 `fetchMyResults`。

管理员结果中心应改成：

- 列表页局部刷新当前页
- 详情页局部更新当前结果
- 非必要不刷新整页

## 三、渲染优化

### 8. 把结果中心从 `App.jsx` 拆成独立模块

至少拆成：

- `ResultsList`
- `ResultDetail`
- `CandidateHistory`
- `ResultsFilters`

这样可以：

- 缩小渲染影响面
- 更容易做懒加载
- 更容易单独优化列表与详情

### 9. 列表页做“摘要先行”

桌面和移动端都一样：

- 首屏先渲染筛选和结果摘要
- 结果列表卡片/行快速出现
- 详情与报表延后

不要让“卷面明细”成为首屏阻塞项。

### 10. 长卷面使用折叠或分段加载

如果一份卷面题量多：

- 不要默认把全部解析全展开
- 按题目卡片折叠
- 优先显示：
  - 题干
  - 用户答案
  - 正误
- 标准答案和解析按需展开

这样可以减少初始 DOM 体积。

## 四、交互性能优化

### 11. 列表与详情分离，不再写回考试主状态

结果详情不应再写到：

- `currentSession`
- `currentQuestions`
- `activeQuestionId`

建议改成独立状态：

- `selectedResultSummary`
- `selectedResultDetail`
- `selectedCandidateHistory`

这样能显著减少不必要重渲染，也能避免答题流和结果流互相污染。

### 12. 详情打开采用“骨架 + 渐进填充”

详情页打开时：

- 第一时间显示顶部骨架
- 先返回分数、通过状态、时间、题型统计
- 卷面题目随后填充

这样用户会感觉更快。

## 五、代码与包体优化

### 13. 管理员结果中心做按需加载

这块功能重、信息密度高，建议独立按需加载，而不是随主界面一起进包。

目标：

- 普通用户进系统时，不需要提前下载管理员结果中心逻辑
- 管理员打开结果中心时再加载对应模块

### 14. 报表和打印逻辑单独拆分

结果报表、打印样式、AI 分析建议属于次级能力，建议懒加载：

- 首次查看列表时不加载
- 用户点击“报表”或“打印”时再加载

## 推荐实施顺序

### 第一阶段：最大收益、最小风险

1. 结果页入口停止并行拉证书与模板
2. 结果列表 API 改为分页摘要
3. 结果详情不再串行双请求，改聚合接口

### 第二阶段：结构优化

4. 结果流与考试流状态拆开
5. 结果中心从 `App.jsx` 拆模块
6. 详情页做缓存与骨架屏

### 第三阶段：进阶优化

7. 长卷面折叠/分段加载
8. 报表和打印懒加载
9. 移动端结果卡片进一步减载

## 验收指标

### 列表页

- 首次打开结果列表不超过 `1` 个核心数据请求
- 当前页渲染稳定，不因证书模块阻塞

### 详情页

- 打开一份结果详情时，不再出现“先等结果，再等会话”的明显双段等待
- 详情首屏先看到摘要，再逐步看到卷面

### 连续查看

- 打开 5 次不同卷面时，页面无明显越来越卡现象
- 返回列表后，筛选状态和滚动位置保留

## 一句话总结

管理员结果中心的性能关键，不是去抠单个函数，而是先把：

- 入口请求
- 列表数据粒度
- 详情接口形态
- 渲染状态边界

这四件事拆对。

## 风险/阻塞
- 若用户快速双击登录、按回车重复提交，或浏览器/页面残留旧请求，已消费验证码会被第二次请求复用，后返回的错误可能误导为“验证码超时”。本次已针对页面端做防重入。
- 如果后续仍出现验证码过期，应优先同时检查三处：`operation_logs` 中 LOGIN_SUCCESS 后是否紧跟 CAPTCHA_INVALID；`captcha_challenges.expires_at` 与当前 UTC 时间差；登录页是否加载了重启后的新 JS。
- Codex 不接触、不保存用户账号密码；登录成功验证仍需要用户本人输入真实凭据。
- Docker `ai-assistant-db-init` 当前会因 `alembic_version.version_num` 字段过短失败：`Data too long for column 'version_num'`，需要后续单独修复迁移版本字段长度；本次为恢复 5193，临时用 `docker compose up -d --no-deps --force-recreate ai-assistant-api` 绕过 db-init。
- 如果登录后仍回启动页，优先检查：18093 是否监听、5193 是否为新镜像、工作台 URL 是否包含并消费 `sso_token`、`/api/ai/session` 是否带 Authorization。

## 可沉淀为长期记忆
- 统一登录验证码有两类易混淆问题：一是 MySQL DATETIME UTC 写入/本地时区解析导致的真过期；二是登录成功后重复提交复用已消费 token 导致的假“过期/超时”。
- 判断是否为重复提交：看操作日志是否出现 LOGIN_SUCCESS 后紧跟 CAPTCHA_INVALID，或同一时间连续多条验证码错误。
- 登录页必须对登录提交做防重入：提交开始同步加锁、禁用按钮、显示“登录中…”，失败刷新验证码后解锁，成功后不再让旧请求恢复登录态。
- 桌面端 SSO 不能只依赖 localhost 跨端口 Cookie；工作台和后端应支持一次性/短期 handoff token 或 Bearer token，并在前端进入后立即清理 URL 参数。
- 本地联调 5180 和 5193 尽量同用 Docker auth/API，避免“桌面打开本地 Node auth，但 AI 后端 introspect Docker auth”的双 auth 服务问题。
- 调试桌面端本地 HTTP 连接时，仍需注意 `AI_ASSISTANT_BUILD_MODE=development`；否则 Rust 侧 production 默认拒绝 HTTP 地址。

## 今日对话摘要

确认 Git 版本管理规则：不同业务系统独立维护版本；同一系统的前端、后端、网关、桌面端共用一个版本号。用户要求以后每次提交都自动关联版本号并推送到 GitHub。

## 今日产出/进展

- 15 个业务系统均建立独立 `VERSION`，初始化为 `1.0.0`。
- 版本规则固定为三位：大改版升第一位，功能优化升第二位，Bug 修复升第三位。
- Git Hook 自动根据提交类型和变更路径升级对应系统版本，amend 原提交并推送当前分支。
- 提交标题自动生成系统版本前缀，例如 `[auth-v1.0.1] fix(auth): 修复登录超时`。
- 已推送实现分支：`codex/independent-system-versioning`。

## 风险/阻塞

- `chore(repo)` 等纯仓库工具提交目前使用 `[repo]` 前缀，不升级业务系统版本；若要求所有提交都必须有数值版本，需要另行定义仓库工具自身的独立版本源。
- 日常工作树原分支尚未合并 `codex/independent-system-versioning`，合并后自动版本 Hook 规则才会在该分支生效。

## 明日计划

- 使用已合并版本规则的工作分支进行日常提交。
- 提交前确认 scope 与实际系统路径一致；共享文件使用具体系统 scope 或 `all`。
- 提交后检查 `git log -1 --pretty=%s`，确认标题含系统版本前缀并已推送远端。

## 可沉淀为长期记忆

- 系统版本互不共用：每个系统只有自己的 `VERSION`，同系统前后端、网关、桌面端保持一致。
- 提交类型映射：`breaking`/`major`/`!` → 主版本；`feat`/`minor`/`perf` → 次版本；`fix`/`patch`/维护类提交 → 修订号。
- 标准流程：`git add` → `git commit -m "类型(scope): 描述"` → Hook 自动同步版本、amend、推送当前分支。
- 不创建、不切换版本号分支；推送始终使用当前 Git 分支。
- 普通业务提交不要使用 `CODEX_VERSIONING_BYPASS=1`，该变量仅用于版本工具自身维护或紧急修复。

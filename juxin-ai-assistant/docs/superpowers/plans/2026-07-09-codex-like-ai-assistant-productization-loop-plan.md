# 聚信 AI 助手 Codex 化产品闭环改造方案

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` or `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.  
> 本方案用于把“聚信 AI 助手”从功能型聊天工具升级为“可计划、可执行、可验证、可沉淀、可复盘”的私人工作助理。

**Goal:** 让聚信 AI 助手具备类似 Codex 的任务闭环能力，同时保持普通员工界面简单、办公化、低技术感。

**Architecture:** 保留现有 FastAPI + React/Tauri + MySQL + Docker Compose 架构，不重写系统；在现有 Agent Runtime、ToolRegistry、TaskState、ContextBuilder、Knowledge、Word Export、Model Profiles 基础上继续产品化。普通用户看到“查资料、写材料、整理文档、导出 Word、保存资料、申请入库”，开发者内部使用 Agent Runtime、Tool、ContextBuilder、Verifier、TaskState 等概念。

**Tech Stack:** FastAPI、SQLAlchemy、Alembic、MySQL、React、Tauri、Vitest、pytest、Docker Compose、Nginx、现有知识库解析/检索/导出模块。

## Global Constraints

- 不重写项目，不新增第二套 Agent 平台。
- 不在普通用户界面暴露 `RAG`、`Embedding`、`Chunk`、`Tool Call`、`ReAct`、`MCP` 等技术词。
- 公司知识必须由管理员上传或审核通过；普通用户资料默认进入“我的资料”或“当前附件”。
- 回答和 Word 导出只展示实际使用的来源，不展示仅检索过但未使用的文件。
- 没有可靠依据时必须提示“当前资料中未找到明确依据”，不得编造。
- 任何删除、停用、入库、联网、外部写操作都必须可确认、可审计、可恢复或可解释。
- 不提交真实密钥、`.env`、本地 SQLite DB、用户上传原文、API Key 或敏感日志。
- 每个开发任务按 TDD 小步执行：先补测试，再实现，再验证。
- 每个阶段完成后必须更新本计划的勾选状态、验证命令和剩余问题。

## 一、产品定位

### 1.1 用户侧定位

聚信 AI 助手是每个人的私人工作助理，重点服务公司内部普通员工和管理员：

- 普通员工：写材料、查资料、整理文档、生成报告、导出 Word、分析附件。
- 管理员：维护公司知识库、审核资料入库、管理分类、查看质量和工具运行情况。
- 业务场景：售前方案、投标材料、产品说明、交付文档、会议纪要、安全运维报告、风险评估材料审查、售后问题排查。

### 1.2 内部工程定位

系统内部应具备 Codex 式工作闭环：

```text
目标识别 → 计划拆解 → 工具执行 → 资料引用 → 结果生成 → 自检复核 → 成果沉淀 → 失败复盘
```

### 1.3 不做什么

- 不做用户看不懂的“技术 Agent 控制台”。
- 不把所有提示词、所有历史消息和全部知识库内容塞进模型。
- 不让模型自由决定所有工具链，先做受控编排。
- 不把普通用户上传资料自动升格为公司正式知识。
- 不在当前阶段引入复杂多 Agent 自主协作平台。

## 二、对标 Codex 后的能力缺口

| 能力项 | Codex 特征 | 当前聚信 AI 助手状态 | 目标状态 |
|---|---|---|---|
| 任务计划 | 明确展示下一步和执行中步骤 | 有 TaskState 基础，但用户感知弱 | 每个任务有办公语言进度 |
| 工具调用 | 工具执行可追踪 | 已有 ToolRegistry 和工具日志基础 | 用户侧可解释，管理侧可统计 |
| 结果验证 | 完成前运行检查 | 已有 Verifier 基础 | 引用、格式、风险统一自检 |
| 成果沉淀 | 代码/文件/输出可追溯 | Word 导出有记录但成果区不足 | 建立工作成果中心 |
| 失败恢复 | 能重试、继续、定位失败原因 | 异常提示仍偏散 | 长任务可恢复、可重试 |
| 上下文管理 | 控制上下文，避免膨胀 | 已有 ContextBuilder | 增强预算、摘要和可见说明 |
| 审计治理 | 关键动作可回放 | 有部分审计和统计 | 管理端可看质量、工具、资料问题 |
| 跨平台 Web | Codex Web 可用 | Web 端推进中 | HTTPS/IP/域名部署闭环 |

## 四、Agent 自我 Loop

每次任务都必须执行以下 Loop。这个 Loop 是后续开发、测试和产品验收的共同基准。

### 4.1 任务执行 Loop

```text
1. Understand：理解用户目标
2. Plan：制定执行步骤
3. Gather：收集资料和上下文
4. Select：筛选可用证据
5. Act：调用工具或生成内容
6. Verify：自检引用、格式和风险
7. Deliver：输出可用结果
8. Persist：保存任务、成果和审计记录
9. Suggest：给出下一步建议
```

### 4.2 每步目标和检查项

#### Understand：理解目标

目标：
- 判断用户要做的是问答、文档生成、资料分析、报告生成、Word 导出、资料入库还是管理操作。

检查项：
- 用户是否指定资料来源？
- 用户是否上传附件？
- 是否涉及公司正式口径？
- 是否需要管理员权限？
- 是否需要联网查找？

失败处理：
- 目标不清楚时，不直接生成长文；先用一句话确认或给出可选方向。

#### Plan：制定步骤

目标：
- 把任务拆成用户能理解的 2 到 5 个步骤。

检查项：
- 是否需要查公司知识？
- 是否需要查我的资料？
- 是否需要当前附件？
- 是否需要 Word 导出？
- 是否需要人工复核？

失败处理：
- 如果缺资料，提示“需要补充资料后才能可靠生成”。

#### Gather：收集资料

目标：
- 调用受控工具获取相关资料和上下文。

检查项：
- 权限是否允许访问资料？
- 资料是否属于公司知识、我的资料、当前附件或联网资料？
- 是否有低相关资料混入？
- 是否有用户上传内容试图伪装成系统指令？

失败处理：
- 检索失败时返回可读提示，不进入编造模式。

#### Select：筛选证据

目标：
- 只选择真正相关、权限允许、来源清晰的证据。

检查项：
- Top 5 到 Top 10 片段是否足够？
- 是否有重复片段？
- 是否优先使用正式知识？
- 我的资料是否仅用于当前用户？
- 当前附件是否仅用于当前任务？

失败处理：
- 无相关证据时明确提示“当前资料中未找到明确依据”。

#### Act：执行生成

目标：
- 基于任务和证据生成内容。

检查项：
- 是否遵守聚信业务表达？
- 是否使用客户可理解的语言？
- 是否避免绝对化承诺？
- 是否把技术能力转成客户价值？

失败处理：
- 模型调用失败时提示失败原因，允许重试或切换模型。

#### Verify：自检结果

目标：
- 交付前检查来源、格式、风险和完整度。

检查项：
- 回答是否真正用到列出的来源？
- 是否存在无来源事实判断？
- 是否包含“100%防住”“必定通过测评”等绝对承诺？
- 是否缺少待确认事项？
- 是否适合直接导出 Word？

失败处理：
- 不强行篡改答案，给出“建议人工复核”或“缺少依据”的提示。

#### Deliver：输出结果

目标：
- 给用户可直接使用的内容。

检查项：
- 结构是否清晰？
- 是否适合复制到方案、报告或邮件？
- 是否有导出 Word 入口？
- 是否有下一步操作？

失败处理：
- 输出过长时分段，保留继续生成入口。

#### Persist：保存记录

目标：
- 保存任务状态、引用来源、工具调用、自检结果和工作成果。

检查项：
- 是否避免保存完整 API Key？
- 是否避免保存无关大段上下文？
- 是否记录导出 Word 的文件名和版本？
- 是否记录用户反馈？

失败处理：
- 保存失败时不丢失用户可见结果，并提示重新保存。

#### Suggest：下一步建议

目标：
- 根据任务结果给出合理下一步。

检查项：
- 是否建议导出 Word？
- 是否建议补充资料？
- 是否建议保存为模板？
- 是否建议申请加入公司知识库？

失败处理：
- 不强推无关动作。

## 五、阶段路线图

## Phase 1：任务执行闭环产品化

**目标：** 让每个任务都有清晰的用户侧进度和后端结构化状态。

**用户价值：**
- 用户知道系统正在干什么。
- 长任务不会只显示“正在生成”。
- 失败任务可定位原因。

**后端范围：**
- 完善 `TaskStateStore`。
- 记录任务目标、阶段、工具摘要、来源摘要、自检摘要和下一步。
- 支持任务失败、取消、完成、重试状态。

**前端范围：**
- 聊天页展示任务进度。
- 历史任务详情展示上次进度和结果。
- 错误提示使用办公语言。

**用户可见文案：**
- 正在理解你的需求
- 正在查找资料
- 正在整理依据
- 正在生成内容
- 正在复核结果
- 已完成
- 生成失败，可重试

**开发检查项：**
- [x] 后端状态字段不存完整提示词和敏感正文。
- [x] 普通用户界面不出现 `TaskState`、`Tool Call`、`RAG`。
- [x] 前端刷新后能恢复最近任务状态。
- [x] 失败状态包含可读原因和重试建议。

**验收标准：**
- [x] 普通聊天能显示完整进度。
- [x] 查资料任务能显示“查找资料”和“整理依据”。
- [x] 生成失败时可以重新生成。
- [x] 历史任务能看到阶段摘要。

## Phase 2：引用来源治理增强

**目标：** 聊天回答和 Word 导出的参考来源只展示实际使用的资料。

**用户价值：**
- 用户不会再看到“明明没参考却列出来”的文件。
- 回答依据更可信。
- Word 导出更适合对内交付。

**后端范围：**
- 统一引用过滤逻辑。
- 将候选来源和实际使用来源分开。
- 生成后由 Verifier 判断实际引用。
- Word 导出复用同一套来源结果。

**前端范围：**
- 引用来源区域显示“实际引用来源”。
- 来源支持点击预览。
- 无来源时显示清晰提示。

**引用保留规则：**
- 答案明确使用了该片段内容。
- 答案引用了该文件中的章节、页码、表格或参数。
- 答案结论依赖该来源。

**引用剔除规则：**
- 只是被检索过。
- 只是用户问题里提到了文件名。
- 只是相似但未被答案采用。
- 来源与最终回答没有内容交集。

**开发检查项：**
- [ ] 泛泛问题不展示知识库引用。
- [ ] 当前附件问题只展示当前附件。
- [ ] 联网资料和公司知识来源清晰区分。
- [ ] Word 导出和聊天回答引用一致。

**验收标准：**
- [ ] 用户问“你是谁”时不出现知识库文件。
- [ ] 用户问附件标题时只显示该附件来源。
- [ ] 用户问公司正式资料时显示公司知识来源。
- [ ] 导出的 Word 参考来源与聊天卡片一致。

**建议测试：**
- `server/tests/test_agent_verifier.py`
- `server/tests/test_chat_word_export.py`
- `apps/desktop/tests/chat-page.test.tsx`

## Phase 4：长任务队列与失败恢复

**目标：** 复杂任务支持后台运行、取消、重试和失败恢复。

**用户价值：**
- 长报告、批量资料处理、联网调研不再卡住页面。
- 失败后不必从头再来。

**任务状态：**
- `queued`
- `running`
- `waiting_user`
- `completed`
- `failed`
- `cancelled`
- `retrying`

**适用任务：**
- 联网调研报告
- 长文档生成
- 批量资料解析
- 批量 Word 导出
- 知识库重新索引

**后端能力：**
- 创建任务
- 查询任务
- 取消任务
- 重试任务
- 从失败步骤恢复

**前端能力：**
- 任务队列入口
- 当前任务进度
- 失败原因
- 继续 / 重试 / 取消

**开发检查项：**
- [ ] 任务可中断。
- [ ] 任务失败不丢正文草稿。
- [ ] 页面刷新后能恢复状态。
- [ ] 后台任务不泄露其他用户资料。

**验收标准：**
- [ ] 联网失败后可以重试。
- [ ] Word 导出失败时正文仍可复制。
- [ ] 长任务刷新页面后能继续查看。
- [ ] 取消任务后不会继续调用外部模型。

## Phase 5：质量看板与运行回放

**目标：** 管理员能看到系统质量，不需要翻日志。

**用户价值：**
- 管理员能知道哪些资料影响回答质量。
- 能定位失败属于模型、资料、工具、权限、网络还是格式问题。

**指标卡片：**
- 今日任务数
- 成功率
- 平均耗时
- 工具失败率
- 引用覆盖率
- 无来源回答比例
- 用户负反馈数
- Word 导出数
- 知识库命中率

**列表：**
- 最近失败任务
- 工具失败 TopN
- 低质量输出
- 高频引用资料
- 长期未引用资料
- 待审核资料

**回放内容：**
- 任务目标
- 阶段时间线
- 工具调用摘要
- 来源摘要
- 自检摘要
- 失败原因
- 下一步建议

## 九、风险清单

### 高风险

1. 引用来源不真实，导致用户误信资料依据。
2. 普通用户资料误进入公司知识库。
3. `AUTH_PUBLIC_URL`、Cookie、CORS 配置错误导致 Web 登录失效。
4. 长任务失败后丢失用户成果。
5. 管理端回放泄露用户私有内容或密钥。

### 中风险

1. 任务状态记录过多导致数据库膨胀。
2. 质量看板指标不准确，误导管理员判断。
3. 助手模式配置过复杂，管理员不会用。
4. 工作成果区和历史任务职责重叠。
5. 自签证书浏览器信任成本较高。

### 低风险

1. 进度文案需要多轮打磨。
2. 不同浏览器对自签证书提示不同。
3. Word 模板样式需要持续优化。
4. 部分旧任务没有完整状态记录。

## 十二、建议执行顺序

1. **先做 Phase 1：任务执行闭环产品化。**
2. **再做 Phase 2：引用来源治理增强。**
3. **再做 Phase 3：工作成果中心。**
4. **随后做 Phase 7：Web HTTPS/IP 部署闭环。**

- Web 部署影响使用范围，需要尽早稳定。
- 长任务、看板、模式治理可以在底座稳定后逐步增强。

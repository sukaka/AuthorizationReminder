## 二、P0 级剩余工作

### 1. 上下文工程重构

状态：已完成最小闭环。`ContextBuilder` 已拆出 `Gather / Select / Compress / Structure` 四步；长历史只保留最近消息，较早消息进入压缩摘要；知识片段按分数去重限量；个人偏好保留在 `long_term_memory`，不作为正式知识依据。

目标：

把当前上下文构建逻辑拆成可控的 Gather、Select、Structure、Compress 四步，避免把历史消息、无关资料或完整文档直接塞进模型。

工作内容：

1. Gather：收集系统提示、公司画像、助手模式、用户问题、最近历史、我的偏好、检索证据、工具结果。
2. Select：按权限、相关性、新近性、资料等级选择上下文。
3. Structure：按 Role、Task、Evidence、Context、Output 组织上下文。
4. Compress：长对话超过阈值后生成摘要，保留关键决策、未完成事项、已确认事实。
5. 将“我的偏好”接入上下文，但只作为偏好，不作为事实证据。

影响范围：

- `server/app/context/context_builder.py`
- `server/app/chat_service.py`
- `server/app/agent_loop/loop_runner.py`
- `server/app/agent_runtime/tools/history_tools.py`
- `server/app/agent_runtime/tools/memory_tools.py`

验收标准：

- 长对话不会无限追加原始历史。
- 用户偏好不会被当作正式知识来源。
- 普通聊天不会自动引用无关知识库文件。
- 上下文中能区分公司知识、我的资料、当前附件、联网资料和个人偏好。

### 2. 引用来源最终治理

状态：已完成后端最小闭环。聊天详情和 Word 导出共用引用匹配逻辑；只保留回答实际提到的资料；重复来源会去重；回答处于“未找到明确依据 / 引用片段没有包含 / 无法确认”等否定证据语境时，即使提到文件名，也不会展示为引用来源。

目标：

回答和 Word 导出只显示真正被回答使用的资料来源，不能把检索过但没用到的文件全部列出。

工作内容：

1. 继续强化回答后的引用过滤。
2. 没有检索命中时，不显示无关参考来源。
3. 如果模型提到了文件名但没有实际检索片段，需要区分“用户提到的文件”和“实际引用来源”。
4. Word 导出和聊天回答保持同一套引用过滤逻辑。

影响范围：

- `server/app/reference_matching.py`
- `server/app/chat_service.py`
- `server/app/chat_word_export.py`
- `server/app/agent_runtime/tools/reference_tools.py`

验收标准：

- 回答中没有实际使用的资料，不出现在“参考来源”。
- 用户问泛泛问题时，不展示上传文件引用。
- Word 导出的参考来源和聊天卡片展示一致。

### 3. 资料入库闭环补齐

状态：已完成后端最小闭环。普通用户上传默认进入“我的资料”；上传后生成摘要，并在未手选有效分类/文档类型时自动建议元数据；提交审核后仍不可被公司知识检索；管理员审核通过后转为 `official_knowledge` 并进入正式公司检索；驳回后保留在个人资料。

目标：

让“上传、解析、摘要、分类、申请入库、管理员审核、正式检索”形成完整闭环。

工作内容：

1. 上传后自动生成摘要。
2. 上传后自动建议一级分类、二级分类和文档类型。
3. 普通用户上传默认保存到“我的资料”。
4. 申请加入公司知识库时必须二次确认。
5. 管理员审核通过后，资料才允许进入公司知识检索。
6. 审核不通过时，资料仍保留在用户“我的资料”。

影响范围：

- `server/app/knowledge_files.py`
- `server/app/knowledge_routes.py`
- `server/app/knowledge_search.py`
- `server/app/agent_runtime/tools/review_tools.py`
- `apps/desktop/src/pages/KnowledgePage.tsx`

验收标准：

- 普通用户上传资料不会自动成为公司知识。
- 管理员审核通过前，公司知识检索查不到该资料。
- 审核通过后，公司知识检索可以命中该资料。
- 审核不通过后，用户仍可在“我的资料”中使用。

### 3. 管理员资料审核体验

## 四、P2 级剩余工作

### 1. 联网调研工作流

状态：已完成工具层最小闭环。新增 `web_research` 工具，可把调研主题拆成 3 到 5 个子问题，逐项联网搜索，汇总为带来源链接的调研报告；搜索日志落库；联网资料不会自动写入公司知识库，报告中明确需要用户确认后再保存。

目标：

将简单联网搜索升级为可控的“联网调研”。

工作内容：

1. Planner：拆成 3 到 5 个子问题。
2. Searcher：执行搜索和网页抓取。
3. Summarizer：总结每个子问题。
4. Reporter：输出最终报告。
5. NoteTool：保存过程笔记。
6. 用户确认后，可以保存到我的资料或申请加入公司知识库。

验收标准：

- 联网资料不会自动成为公司正式知识。
- 报告能显示来源链接。
- 搜索失败时能降级为普通回答，并明确说明未联网成功。

### 2. 基础评估体系

状态：已完成后端最小闭环。管理员统计接口已包含工具调用成功率、知识检索命中率、回答引用覆盖率、无来源回答比例、Word 导出次数和工具错误分布；部门经理接口仍只返回部门范围内生成统计，避免跨部门泄漏日志指标。

目标：

内测阶段能量化质量，而不是只靠主观判断。

指标：

1. 工具调用成功率。
2. 知识检索命中准确率。
3. 回答引用来源覆盖率。
4. 无来源回答比例。
5. 文档生成格式合格率。
6. 用户上传文件分类准确率。
7. 入库权限控制正确率。
8. 用户反馈满意度。

验收标准：

- 管理员能看到基础质量统计。
- 每次失败有错误码和排查线索。
- 可以抽样回放一次任务的工具调用和引用来源。

### 3. 延后能力

以下能力暂不作为当前主线：

1. PPT 生成工具。
2. 深度联网调研增强版。
3. 高级质量评分工具。
4. 批量资料治理工具。
5. 外部向量库接入工具。
6. MCP / A2A 适配工具。

## 五、建议执行顺序

### 第一批：稳定 Agent 内核

1. 拆分 ContextBuilder 为 Gather、Select、Structure、Compress。
2. 接入个人记忆到上下文。
3. 完成长对话压缩。
4. 完善引用来源过滤。

原因：

这是 Agent 能不能稳定工作的核心。先做这里，后续前端和资料库体验才不会建在不稳定基础上。

### 第二批：补齐资料入库闭环

1. 上传后生成摘要。
2. 自动建议分类和文档类型。
3. 入库申请二次确认。
4. 管理员审核通过后进入正式检索。

原因：

资料库是聚信 AI 助手的核心资产入口，必须先保证权限和流程正确。

### 第三批：优化用户界面

1. 聊天页资料来源和紧凑附件条。
2. 我的资料页重做交互。
3. 管理员审核体验。
4. 历史任务体验。

原因：

当前功能逐步具备，但用户界面仍需要产品化，尤其要减少后台感和技术词。

### 第四批：评估和质量看板

1. 工具调用成功率。
2. 引用来源覆盖率。
3. 无来源回答比例。
4. 用户反馈满意度。

原因：

进入内测后，必须能知道哪里失败、为什么失败、用户是否满意。

## 六、当前不建议做的事

1. 不建议马上做复杂多 Agent 自主协作。
2. 不建议马上接 MCP / A2A 作为主架构。
3. 不建议马上引入外部向量库替代现有检索。
4. 不建议让模型自由决定所有工具链。
5. 不建议把联网资料自动写入公司知识库。
6. 不建议在普通用户界面暴露 RAG、Memory、Tool Call、Embedding 等术语。

## 七、下一步最小任务建议

建议下一步只做一个小闭环：

1. ContextBuilder 拆分为 Gather、Select、Structure、Compress。
2. 写最小测试：
   - 普通聊天不带无关资料。
   - 当前附件问答只带当前附件。
   - 我的偏好只影响输出风格，不作为事实来源。
   - 长对话超过阈值后生成摘要。
3. 跑后端相关回归。
4. 更新路线图。

完成这个小闭环后，再进入资料入库摘要和分类建议。

## 1. 整合结论

两份原规划不是互相替代关系，而是层级不同：

- `6.0/7.0 产品与研发计划`负责定义两个大版本的产品方向、业务范围和长期路线。
- `智能成长与多 Agent 研发实施方案`负责解决统一回复、运行时、多 Agent、自检、学习和治理的近期技术落地。

正确处理方式不是简单合并章节，而是将“智能成长与多 Agent”方案整体纳入 6.0，作为 6.0 的基础能力和前 8 周 MVP；7.0 在此基础上扩展外部 Agent Gateway、渠道连接、跨平台协作和数据出域治理。

整合后的版本关系：

```text
5.x 现有基础
├── 知识问答
├── 资料管理
├── 基础长任务
├── 学习中心
└── 治理中心
        │
        ▼
6.0 企业任务工作台
├── 统一问答与热点闭环
├── 统一 Run/Step 任务底座
├── 受控的内部多 Agent
├── 深度检索与可信引用
├── 成果生成与版本管理
├── 自检、评测与学习闭环
└── 企业治理和运营
        │
        ▼
7.0 企业 Agent Hub
├── Agent Gateway
├── 飞书和企业微信渠道
├── Kimi 等外部智能体
├── 即梦等视觉生成能力
├── 智能路由与跨 Agent 工作流
├── 数据出域、审计和成本治理
└── Agent 市场与低代码编排
```

### 1.1 核心版本定义

**6.0：从“能回答”升级为“能完成、会复核、可成长”。**

**7.0：从“一个助手”升级为“能够安全调度多个厂商 Agent 的企业 Agent 平台”。**

### 1.2 原方案能力归属

| 原“智能成长与多 Agent”能力 | 新版本归属 | 处理方式 |
|---|---|---|
| FAQ 统一问答 | 6.0 P0 | 作为低延迟、零模型调用入口 |
| 热点问题转 FAQ | 6.0 P0 | 纳入内容治理闭环 |
| 统一 Run/Step | 6.0 P0 | 作为任务底座，不另建 `ai_tasks` |
| NativeRuntime | 6.0 P0 | 默认生产运行时 |
| LangGraphRuntime | 6.0 P1 | 仅复杂报告试点，功能开关控制 |
| Coordinator/Researcher/Writer/Reviewer | 6.0 P1 | 内部专业角色，按任务动态启用 |
| ModelGateway | 6.0 P0 | 7.0 Agent Gateway 的模型层基础 |
| 运行时自检 | 6.0 P0/P1 | 成为所有正式成果的交付门禁 |
| 离线评测与影子运行 | 6.0 P1 | 用于 Prompt、工作流和模型灰度 |
| 学习候选与审核发布 | 6.0 P1 | 受控成长，不允许自动发布生产 |
| 学习中心改版 | 6.0 P1 | 合并为偏好、模板和改进记录 |
| 治理中心改版 | 6.0 P1 | 扩展为内容、能力、质量安全三组 |
| 外部 Agent/渠道 | 7.0 | 由 Agent Gateway 统一接入 |

### 1.3 必须统一的冲突项

1. **任务表统一使用 `ai_agent_runs`。** 产品层称“任务”，技术层称 Run，不再同时新增 `ai_tasks`。
2. **步骤表统一使用 `ai_agent_run_steps`。** checkpoint、模型调用、工具调用和错误均记录在步骤中。
3. **成果统一使用 `ai_artifacts`。** Word、PPT、Excel、PDF、Markdown 和图片均为 Artifact。
4. **6.0 周期统一为 24～28 周。** 原 8 周计划定义为 6.0 MVP，不代表完整 6.0 GA。
5. **7.0 周期统一为 28～34 周。** 必须在 6.0 任务底座稳定后开始。
6. **内部多 Agent 属于 6.0，外部厂商 Agent 属于 7.0。** 二者使用同一任务协议，但权限边界不同。
7. **确定性逻辑不 Agent 化。** FAQ、权限、事务、文件生成、格式校验、发布和删除继续由普通代码完成。

## 2. 总体建设原则

1. 保留现有 `agent_loop`、`agent_runtime`、知识检索、长任务、学习中心和治理中心，不进行全量重写。
2. 建立项目自有的 Run、Step、Event、Artifact、Citation 和 Agent Capability 契约，不把第三方框架对象暴露给 API。
3. 简单请求走最短路径，复杂任务才启用多步骤和多 Agent。
4. 所有关键结论必须可追溯到资料、规则或明确标记的 AI 推断。
5. 用户反馈只能形成学习候选，公司级规则必须评测、审核、灰度和可回滚。
6. 第三方 Agent 默认不可信，调用前执行权限与数据出域判断，调用后执行结果复核。
7. 所有新能力均通过功能开关灰度，不在同一版本删除旧接口和旧数据。
8. 前端使用办公语言，不显示 RAG、Embedding、ReAct、Node、Tool Call 等工程术语。

# 第一部分：6.0 企业任务工作台

## 3. 6.0 建设目标

### 3.1 产品目标

用户可以把一项真实工作交给 AI，系统能够：

1. 识别任务目标、受众、资料范围和成果类型。
2. 判断走统一回复、普通问答、固定工作流还是复杂任务。
3. 查找多份资料并显示真实引用。
4. 生成计划并在后台持续执行。
5. 输出 Word、PPT、Excel、PDF 或 Markdown 成果。
6. 在交付前检查事实、引用、格式、安全和完整性。
7. 保存任务过程、成果版本和审计记录。
8. 从用户纠正和失败任务中形成受控的改进候选。

### 3.2 典型场景

- 查询公司统一政策并获得稳定口径。
- 根据管理员手册回答命令行操作问题并定位原文。
- 汇总多份建设方案，生成客户汇报材料。
- 根据产品资料生成培训 PPT 和讲师讲稿。
- 根据测试记录生成测试报告和缺陷分析。
- 对比文档多个版本并输出变更说明。
- 根据会议记录生成纪要、待办和责任人。
- 根据 Excel 数据生成分析报告和汇报图表。

### 3.3 非目标

- 不允许 Agent 自动修改并发布生产代码。
- 不允许用户上传内容未经审核自动成为正式公司知识。
- 不允许模型决定权限或绕过服务端规则。
- 不为每个部门常驻一个独立 Agent。
- 不让多个 Agent 处理所有简单问答。
- 不允许学习候选绕过评测和审核直接生效。

### 4.1 请求路由顺序

所有请求固定按以下顺序处理：

1. 身份、会话、输入和附件安全检查。
2. 权限范围和资料范围确认。
3. FAQ 精确、别名和严格语义匹配。
4. 固定业务流程识别。
5. 意图、复杂度和风险判断。
6. 选择直接回复、单 Agent、确定性工作流或内部多 Agent。
7. 保存 Run、Step、Event 和 checkpoint。
8. 执行交付前自检。
9. 保存 Artifact、Citation、质量结果和审计记录。
10. 异步聚合反馈并生成学习候选。

### 4.2 路由矩阵

| 场景 | 路径 | 最大模型调用 | 是否创建完整任务 |
|---|---|---:|---|
| FAQ | 规则直接回复 | 0 | 记录轻量 Run |
| 闲聊/润色 | 单 Agent | 1 | 是 |
| 知识事实问答 | 检索 + 单 Agent + 引用检查 | 1～2 | 是 |
| 固定审批/入库 | 确定性工作流 | 0～1 | 是 |
| 多资料汇总 | Researcher + Writer + Reviewer | 2～4 | 是 |
| 正式成果 | 多步骤工作流 + 人工门禁 | 2～6 | 是 |
| 学习更新 | 离线评测工作流 | 1～2 | 是，不进入用户对话 |

## 5. 6.0 核心能力

### 5.1 统一问答与热点闭环

匹配顺序：

1. 标准问题完全匹配。
2. 管理员维护的相似问法完全匹配。
3. 空白、大小写、标点和全半角规范化匹配。
4. 严格阈值的语义匹配。
5. 未命中后进入正常任务路径。

要求：

- FAQ 命中后不调用模型。
- 返回 FAQ ID、版本、命中类型和依据。
- 支持草稿、待发布、已发布、停用、回滚和生效时间。
- 热点问题可以一键生成 FAQ 候选和相似问法。
- 发布前回放历史问题并检查与现有 FAQ 的冲突。
- 对话只显示“统一回复”，不显示模型调用等技术信息。

### 5.2 统一任务 Run/Step

产品界面称“任务”，技术模型统一称 Run。

Run 状态：

```text
created → queued → running → waiting_confirmation → completed
                       ├→ paused
                       ├→ retrying
                       ├→ cancelled
                       └→ failed
```

必须解决：

- A 任务的回复不会出现在 B 任务。
- 用户切换页面后后台继续执行。
- 刷新后恢复任务进度和已生成草稿。
- SSE 断线重连后不重复追加消息。
- 支持取消、重试、从 checkpoint 继续和保留草稿。
- 每个步骤有最大模型次数、工具次数、Token 和超时预算。
- 重复投递不产生重复成果和重复外部动作。

### 5.3 AgentRuntime 适配层

项目定义统一接口：

```python
class AgentRuntime(Protocol):
    async def start(self, request: RunRequest) -> RunSnapshot: ...
    async def resume(self, run_id: str, command: ResumeCommand) -> RunSnapshot: ...
    async def cancel(self, run_id: str) -> RunSnapshot: ...
    async def inspect(self, run_id: str) -> RunSnapshot: ...
```

实施策略：

- `NativeRuntime` 组合现有 LoopRunner、ToolRegistry、LongTask、QualityChecker 和 Verifier，作为默认生产运行时。
- `LangGraphRuntime` 只试点复杂报告，不直接替换所有流程。
- API、前端和数据库只依赖项目契约，不依赖框架内部状态对象。
- LangGraph 试点不达标时直接关闭开关，NativeRuntime 继续运行。

### 5.4 内部专业 Agent

只在复杂任务中按需启用：

**Coordinator**

- 判断任务目标、资料范围、风险、成果和预算。
- 只能从注册工作流中选择，不允许任意创建未知流程。

**Researcher**

- 拆分检索子问题。
- 分公司资料、个人资料和当前附件检索。
- 输出证据卡片、冲突和资料缺口，不直接写长文。

**Writer**

- 只根据用户目标、批准的结构和证据写作。
- 无依据内容标记“待确认”，不补造事实。

**Reviewer**

- 检查事实、引用、格式、敏感信息和绝对化承诺。
- 最多自动退回 Writer 两次，之后进入人工复核。

**Learning Worker**

- 离线聚合热点、纠正、失败和人工修改。
- 只生成候选和评测报告，不直接发布。

### 5.5 深度检索与可信引用

动态召回策略：

| 任务 | 默认召回 | 建议上限 |
|---|---:|---:|
| 精准事实 | 12 | 16 |
| 多资料汇总 | 16～20 | 24 |
| 跨版本对比 | 每版本 8～12 | 总计 24 |
| 复杂成果 | 分阶段检索 | 每阶段 24 |

检索要求：

- 关键词、语义、标题和目录混合召回。
- 查询扩展、同义词、简称和命令词识别。
- 多文档覆盖约束，避免只查一个文档。
- 相似片段去重和相邻章节补全。
- 证据不足时自动二次检索。
- 权限在检索前过滤。
- 引用记录文件、版本、章节、页码和片段。
- 点击引用胶囊定位原文。
- 只展示实际用于回答的引用。
- 明确区分原文事实、AI 推断和通用建议。

### 5.6 文档版本与资料治理

- 同名上传选择“独立资料”或“更新现有版本”。
- 保留版本时间线、说明、上传人和变更原因。
- 自动生成版本差异摘要。
- 指定当前生效版本和参与检索版本。
- 历史版本默认不参与检索，可查看、比较和恢复。
- 引用固定到具体文件版本。
- 自动识别重复、近似、过期和冲突资料。
- AI 建议分类、文档类型、标签、摘要、权限和有效期。
- 正式知识的自动建议必须经管理员确认。

### 5.7 成果生成中心

支持：

- Word：方案、报告、制度和总结。
- PPT：培训、宣讲、汇报和讲稿。
- Excel：清单、台账、分析和图表。
- PDF：正式交付和固化版本。
- Markdown：技术文档和知识文章。
- 文本：邮件、通知和消息。

统一流程：

```text
选择成果类型
→ 选择模板、资料、受众和风格
→ 生成提纲
→ 用户确认或直接执行
→ 后台生成
→ 质量审核
→ 在线预览与局部修改
→ 导出、保存或归档
```

### 5.8 运行时自检

每次正式回答或成果交付前检查：

1. Schema、章节和必填内容。
2. 引用存在性、权限、位置和相关性。
3. 重要事实是否有证据。
4. 敏感信息、越权和危险操作。
5. 用户偏好、模板和禁用表达。
6. 是否完整完成用户目标。

处理策略：

- 高风险失败：禁止直接交付。
- 中风险失败：最多自动修订两次。
- 达到上限：保留草稿并转人工复核。
- 自检失败不删除用户已生成内容。

### 5.9 自我学习与成长闭环

学习来源：

- 点赞、点踩和原因。
- 用户明确纠正。
- 管理员修改 FAQ、模板和成果。
- 高频问题与低相关检索。
- 长任务失败、重试和人工接管。
- 评测集失败项。

候选类型：

- 个人偏好
- 纠错规则
- FAQ
- 模板
- 知识维护
- Prompt 修订
- 新能力建议

状态机：

```text
draft → evaluated → staged → published
                          ├→ rolled_back
                          └→ superseded
```

发布保护：

- 单个用户的一次反馈不能直接变为公司规则。
- 公司候选必须关联来源、影响范围和回滚版本。
- 发布前运行核心评测集和专项评测集。
- 安全用例必须全部通过。
- 新版质量不能低于当前生产版本。

### 5.10 模板与岗位助手

企业模板保存结构、输入字段、资料范围、Prompt 版本、品牌样式、审核流程和权限。

首批模板：

- 项目周报
- 测试计划和测试报告
- 缺陷分析
- 项目验收清单
- 客户培训 PPT
- 产品介绍 PPT
- 会议纪要
- 故障分析
- 整改建议
- 产品方案和对比报告

岗位助手：销售、售前、测试、项目、运维、培训、行政人事和管理助手。岗位助手共享底层任务系统，只改变默认模板、知识范围、工具和引导。

### 5.11 前台体验

对话主界面：

- 左侧会话和任务历史。
- 中间对话和成果正文。
- 右侧按需展开任务详情、资料、质量和成果。
- 小屏时右侧变抽屉，左侧可收起。

进度展示：

```text
✓ 已理解需求
✓ 已找到 5 条相关资料
● 正在整理报告
○ 复核引用和格式
```

学习中心合并为：

1. 我的偏好
2. 常用模板
3. 改进记录

治理中心分组：

```text
内容治理：统一问答、热点问题、资料治理、模板审核
能力治理：助手能力、工作流、模型与预算
质量安全：质量看板、学习候选、运行记录、审计日志
```

### 5.12 管理运营

管理员关注可行动信息：

- 哪些问题没有答案或引用不足。
- 哪些资料经常检索不到。
- 哪些回答被人工大幅修改。
- 哪个工作流耗时或成本异常。
- 哪些文档过期、重复、解析失败或长期未命中。
- 哪些学习候选等待审核。
- FAQ 命中率、任务完成率和用户满意度。

|---|---|---|

## 7. 6.0 性能、安全与运维

### 7.1 缓存分层

- 浏览器：静态资源和非敏感配置。
- 进程内存：字典、短期模型配置和资料目录。
- Redis：会话、任务状态、队列、锁、热点 FAQ、限流。
- 检索缓存：规范化问题到候选片段 ID，权限变更时失效。
- Embedding 缓存：相同文本不重复向量化。
- 文档摘要缓存：按文件版本保存。
- 成果中间态：checkpoint 和局部重生成。

### 7.2 性能目标

| 场景 | P95 目标 |
|---|---:|
| FAQ | 1 秒内完成 |
| 普通问答首字 | 3 秒内 |
| 知识问答首字 | 8 秒内 |
| 简单知识回答完成 | 30 秒内 |
| 复杂任务确认 | 2 秒内返回任务 ID |
| 页面恢复任务 | 2 秒内 |

### 7.3 安全规则

- 检索前权限过滤。
- 成果继承来源中最严格的权限。
- 多 Agent 只传递最小必要上下文。
- 对外发送、发布、删除和覆盖由确定性代码执行。
- 敏感任务必须进入人工门禁。
- Prompt Injection 内容视为不可信数据，不能改变系统规则。
- 管理员默认不能查看用户完整正文；敏感查看需要更高权限并记录审计。

### 7.4 降级顺序

1. LangGraph 故障切回 NativeRuntime。
2. Reviewer 模型故障时执行确定性检查并标记人工复核。
3. 向量检索故障时降级关键词检索。
4. Redis 故障时关闭缓存，幂等和任务状态回到数据库。
5. 主模型故障时 FAQ 保持可用，生成任务进入备用或重试。
6. 长任务故障保留 checkpoint 和草稿。

## 9. 7.0 建设目标

## 11. 7.0 核心能力

### 11.1 Agent 接入中心

- 新增、测试、启用、停用和删除连接。
- 管理 API 地址、认证、回调和密钥。
- 配置适用人员、部门、任务和数据等级。
- 配置超时、并发、每日限额和预算。
- 查看健康状态、调用记录和错误。
- 配置备用 Agent 和降级策略。

凭证必须加密、掩码、可轮换、不可进入 Prompt 和普通日志。

### 11.2 能力注册协议

每个 Agent 注册：

- ID、名称、厂商和版本。
- 能力标签和使用说明。
- 输入、输出和附件 Schema。
- 同步、流式、异步和回调能力。
- 超时、并发、限流和重试策略。
- 数据出域等级。
- 预计质量、耗时和成本。
- 健康状态和服务级别。

### 11.3 智能路由

选择顺序：

1. 权限、数据等级和出域策略过滤。
2. 用户明确指定且允许时优先。
3. 按能力、质量、延迟、成本和健康度评分。
4. 失败时按策略切换备用 Agent。
5. 路由原因写入审计。

### 11.4 多 Agent 协作

支持串行、并行、条件、人工审核、重试、备用切换、补偿和子任务合并。

```text
检索产品资料
→ 写作 Agent 生成内容
├→ PPT Agent 生成课件
└→ 即梦生成视觉素材
→ Reviewer 检查事实、引用和品牌规范
→ 负责人确认
→ 飞书发送
→ Artifact 归档
```

### 11.5 飞书

- 私聊、群聊发起任务。
- 返回进度、引用和成果。
- 读取授权文档、日历、任务和消息。
- 创建待办、日程和通知。
- Web 与飞书任务互相跳转。
- 用户、部门和群聊身份映射。

群聊不能自动使用提问者私人资料，回复必须绑定原消息、群聊和 Run ID。

### 11.6 企业微信

- 内部问答、任务发起、群通知和成果发送。
- 员工身份映射和部门权限同步。
- 审批、完成和异常提醒。
- 客户沟通内容草拟。

对外发送必须人工确认，7.0 首版不默认自动发送客户。

### 11.7 Kimi 等外部智能体

- 长文档分析和专业推理。
- 复杂写作和备用模型通道。
- 调用前做权限、出域和脱敏判断。
- 仅发送任务所需最小内容。
- 外部结果仍经过内部 Reviewer 和引用检查。

### 11.8 即梦等视觉能力

- PPT 封面、插图和产品宣传图。
- 培训素材、短视频和动态内容。
- 公司品牌词、禁用词、尺寸和风格规范。
- 保存提示词、结果、审核、版权提示和用途。

### 11.9 跨平台任务同步

- 任意渠道发起的任务使用同一 Run ID。
- Web、飞书和企业微信共享状态、成果、引用和审计。
- 各渠道保存独立消息定位信息。
- 管理员可在 Web 审核，结果返回原渠道。
- 移动端取消后后台立即停止未执行步骤。

### 11.10 统一身份与数据出域

```text
系统用户
├── 飞书身份
├── 企业微信身份
├── 部门、岗位和角色
├── 可访问知识库
├── 可调用 Agent
├── 可用业务工具
└── 可发送对象范围
```

| 数据等级 | 规则 |
|---|---|
| L0 公开 | 可发送至授权外部 Agent |
| L1 内部 | 仅发送必要片段并记录审计 |
| L2 敏感 | 脱敏并经确认后方可出域 |
| L3 机密 | 仅本地模型和内部 Agent |

### 11.11 审计与成本

每次调用记录用户、渠道、Run、Step、Agent、路由原因、资料 ID、数据等级、脱敏、耗时、状态、成本、成果和后续发送对象。

运营看板显示：

- Agent 调用量、成功率和 P95。
- 单任务和部门月度成本。
- 降级、故障和熔断次数。
- 人工修改率和满意度。
- 同类任务中不同 Agent 的效果。

### 11.12 Agent 市场和低代码编排

- 浏览、安装、授权和停用内部 Agent。
- 展示能力、权限、成本和适用场景。
- 提供 Connector SDK 和发布规范。
- 拖拽配置触发器、检索、Agent、判断、审核、生成、发送和归档。

## 19. 风险与应对

| 风险 | 应对 |
|---|---|
| 范围过大 | 按 MVP、GA、Agent Hub 三个门禁推进 |
| 框架锁定 | 项目自有 Runtime 契约，LangGraph 仅试点 |
| 多 Agent 成本高 | 简单请求最短路径、预算和模型路由 |
| 检索漏召回 | 混合检索、二次检索和标准评测 |
| 任务串线 | 全链路 Run ID、权限校验和并发 E2E |
| 成果格式不稳定 | 模板化、渲染校验和人工门禁 |
| 学习污染 | 候选、评测、审核、灰度和回滚 |
| 外部服务不稳定 | 超时、熔断、降级和备用 Agent |
| 敏感数据出域 | 分级、最小数据、脱敏、审批和审计 |
| 成本失控 | 用户/部门预算、限额和成本看板 |
| 厂商接口变化 | Connector 适配层和合约测试 |

## 20. 发布与回滚

统一发布顺序：

```text
开发环境
→ 自动测试与评测
→ 管理员账号
→ 5% 用户
```

关键功能开关：

- `FAQ_MATCH_ENABLED`

- `DATA_EGRESS_ENABLED`
- `AGENT_AUTO_ROUTING_ENABLED`

回滚要求：

- API 向后兼容一个完整大版本。
- 数据迁移优先新增，不在同版删除旧字段。
- 新 Runtime 异常切回 NativeRuntime。
- FAQ、Prompt、工作流、模板和学习候选独立版本回滚。
- 外部 Agent 可按厂商、能力、部门一键停用。

## 22. 最终成功标准

6.0 成功的标准：用户能把真实工作交给 AI，并获得有依据、可编辑、可审核、可恢复、可归档的成果；系统能从反馈中形成受控改进，而不是无约束自我修改。

7.0 成功的标准：聚信 AI 助手能在统一身份、权限、数据出域、审计和成本控制下，稳定调度多个厂商 Agent 完成跨平台任务；用户无需理解背后的接口差异。

最终产品形态：

> 聚信 AI 助手负责理解用户、掌握企业知识和统筹任务；内部与外部 Agent 提供专业能力；平台负责权限、安全、审计、成本和成果沉淀。

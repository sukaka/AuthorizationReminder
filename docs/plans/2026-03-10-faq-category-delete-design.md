# FAQ Category Delete Design

**Date:** 2026-03-10

## Goal

让 FAQ 系统的分类管理支持：

- 单个删除分类
- 批量删除分类
- 删除前阻止删除仍被 FAQ 引用的分类
- 删除前阻止删除仍有子分类的父分类

本次只补齐分类管理能力，不扩展分类迁移、递归删除或级联删除。

## Current State

后端当前已有 `DELETE /api/faq/categories/:id`，但只有一层校验：

- 分类不存在时报错
- 分类下仍有关联 FAQ 时报错

当前缺口：

- 没有“存在子分类不可删除”的规则
- 没有批量删除接口
- 前端分类管理页没有删除按钮、没有勾选态、没有批量删除入口
- 现有 smoke 测试没有覆盖分类删除规则

## Recommendation

采用“后端统一校验 + 前端显式交互”的方案：

1. 后端抽出分类删除校验逻辑，供单删和批量删除复用
2. 新增批量删除接口，逐个返回成功/失败结果
3. 前端分类管理页增加单删、复选框和批量删除按钮
4. 保持失败原因可读，避免前端自行拼接复杂判断

不采用前端循环调用单删接口，因为：

- 错误汇总不稳定
- 成功/失败状态不容易统一展示
- 后续扩展审计和返回结构会更乱

## Delete Rules

删除分类时统一执行以下规则：

1. `id` 必须是有效正整数
2. 分类不存在时返回 `404`
3. 若有 FAQ 文章引用该分类且文章未删除，返回 `409`
4. 若有任意子分类 `parent_id = 当前分类id`，返回 `409`

错误文案口径：

- `该分类下有FAQ，无法删除`
- `该分类下有子分类，无法删除`

## API Design

### Existing Single Delete

保留：

- `DELETE /api/faq/categories/:id`

返回：

- 成功：`{ ok: true }`
- 失败：沿用统一错误结构

### New Batch Delete

新增：

- `POST /api/faq/categories/batch-delete`

请求体：

```json
{
  "ids": [11, 12, 13]
}
```

响应体：

```json
{
  "ok": true,
  "total": 3,
  "success_count": 2,
  "failure_count": 1,
  "deleted_ids": [11, 12],
  "failures": [
    { "id": 13, "error": "该分类下有子分类，无法删除" }
  ]
}
```

设计约束：

- 允许部分成功
- `ids` 去重后处理
- 空数组或无有效 ID 返回 `400`
- 审计日志按每个实际删除成功的分类逐条写入，保持与单删一致

## Frontend Design

分类管理页新增三类交互：

### 1. 行内删除

- 每行操作区新增 `删除`
- 点击后弹窗二次确认
- 成功后刷新分类列表

### 2. 勾选选择

- 表头增加全选框
- 每行增加单选框
- 编辑态和勾选态相互独立，不联动重置表单

### 3. 批量删除

- 表格上方增加批量操作栏
- 至少选择一项后可点击 `批量删除`
- 删除完成后展示汇总消息：
  - 全部成功：`已删除 N 个分类`
  - 部分失败：`删除完成：成功 X 个，失败 Y 个`
- 若存在失败项，优先展示前几条失败原因

## Error Handling

前端不预判“是否可删”，统一以接口返回为准。

这样可以避免：

- 前端本地数据滞后
- 批量操作时规则不一致
- 后续约束增加后前端忘记同步

## Testing

后端 smoke 用例增加：

1. 创建父分类、子分类、可删分类
2. 给一个分类绑定 FAQ，验证单删返回 `409`
3. 删除父分类，验证因子分类存在返回 `409`
4. 调用批量删除，验证：
   - 可删分类成功
   - 有 FAQ 的分类失败
   - 有子分类的分类失败
5. 读取分类列表，确认成功删除的分类已不存在

前端当前无测试基建，本次通过后端测试 + 前端构建验证。

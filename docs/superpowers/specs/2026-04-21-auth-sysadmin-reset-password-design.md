# 认证中心 sysadmin 用户重置密码设计

## 背景

当前认证中心已经具备以下能力：

1. 用户表存在 `must_change_password` 字段。
2. 登录链路已支持“首次登录请先修改密码”的强制改密拦截。
3. 管理端已有“重置密码”入口和后端接口。

但现有实现尚未完整满足这次需求中更严格的规则：

1. 只有 `sysadmin` 可以重置密码。
2. `sysadmin` 只能重置非 `sysadmin` 账号。
3. 重置密码后必须强制改密。
4. 重置后必须立即让目标用户现有会话失效。
5. 重置密码固定为 `!b$#+^o9uF`。

这次需求不是新增一套“找回密码”流程，而是收紧并统一后台账号密码重置规则。

## 目标

实现一套明确、可测试、可审计的后台密码重置规则：

1. 只有 `sysadmin` 可以执行密码重置。
2. `sysadmin` 不可重置自己。
3. `sysadmin` 不可重置任何 `sysadmin` 账号。
4. `sysadmin` 可重置所有非 `sysadmin` 账号。
5. 重置后目标账号密码固定为 `!b$#+^o9uF`。
6. 重置后目标账号 `must_change_password = 1`。
7. 重置后目标账号现有会话立即失效。
8. 目标用户下次登录时走现有“首次登录请先修改密码”流程。

## 非目标

1. 不新增“短信找回密码”“邮箱找回密码”等自助找回流程。
2. 不做密码随机生成功能。
3. 不把重置密码规则做成系统配置项。
4. 不新增第二套强制改密页面，继续复用现有流程。

## 方案对比

### 方案 A：直接在现有接口中硬编码规则

做法：在现有重置密码接口里直接加入权限判断、固定密码、强制改密、会话吊销。

优点：改动最小，上线快。

缺点：

- 权限和行为规则散在 handler 中，后续维护容易变乱。
- 单测粒度不够清晰。

### 方案 B：将重置密码规则收口为独立服务

做法：新增专门的重置密码规则函数/服务，接口层只负责调用它并返回结果。

优点：

- 权限边界清晰。
- 更容易补齐单测。
- 后续若规则再变化，改动集中。

缺点：

- 比直接在接口里硬编码多一点整理成本。

### 方案 C：将默认重置密码与规则做成可配置

做法：把默认密码和行为策略放入安全配置中，由后台页面维护。

优点：灵活。

缺点：

- 当前需求已明确固定密码。
- 配置化反而增加误配置风险与测试成本。

## 结论

采用方案 B：将重置密码规则收口为独立服务，并复用现有接口与现有强制改密流程。

## 行为规则

### 权限规则

1. 只有 `sysadmin` 可以执行重置密码操作。
2. 非 `sysadmin` 调用重置密码接口时返回 403。
3. `sysadmin` 不能重置自己。
4. `sysadmin` 不能重置任何 `sysadmin` 用户。
5. `sysadmin` 可以重置所有非 `sysadmin` 用户，包括：
   - `admin`
   - `auditor`
   - `editor`
   - `reviewer`
   - 普通业务用户

### 重置结果

执行重置后，系统必须同时完成：

1. 将目标用户密码更新为固定密码 `!b$#+^o9uF` 的 hash。
2. 将 `must_change_password` 设置为 `1`。
3. 吊销目标用户全部现有有效会话。
4. 记录 `RESET_PASSWORD` 审计日志。

### 登录后行为

目标用户使用重置密码登录后：

1. 登录凭证校验通过。
2. 因 `must_change_password = 1`，不直接进入系统主页。
3. 进入现有“首次登录请先修改密码”流程。
4. 修改密码成功后，将 `must_change_password` 清为 `0`。
5. 修改密码成功后，继续沿用现有“重新登录”或现有改密完成后的登录流程，不新增额外流程。

## 后端设计

### 规则收口

建议在认证模块新增一个独立的重置密码规则函数，例如：

- 输入：操作者、目标用户 ID
- 输出：目标用户基本信息与操作结果

该函数统一负责：

1. 校验操作者角色是否为 `sysadmin`
2. 查询目标用户
3. 校验目标用户是否存在
4. 校验目标用户不是 `sysadmin`
5. 校验目标用户不是操作者自己
6. 生成固定密码 hash
7. 更新 `password_hash`
8. 更新 `must_change_password = 1`
9. 吊销目标用户所有 session
10. 写审计日志

这样现有接口只保留“调用规则函数 + 返回结果”的职责。

### 固定密码

本次固定密码为：

- `!b$#+^o9uF`

该值按当前需求固定，不通过前端传入，也不由接口参数决定。

### 返回结构

接口返回建议保持简洁：

- `success`
- `user_id`
- `username`

不要求接口把明文密码再次回传给前端；前端提示文案直接使用固定值即可。

这样可以减少接口日志、代理日志、抓包误暴露明文密码的机会。

### 会话吊销

重置密码后必须立即执行目标用户会话吊销。

要求：

1. 被重置用户所有现有有效 session 立即失效。
2. 被重置用户在其他浏览器/设备上的后续请求应被视为未登录或会话失效。
3. 此逻辑继续复用现有的 session 吊销能力，而不是另写一套 session 删除逻辑。

## 前端设计

### 用户列表操作

继续复用现有“重置密码”按钮，但收紧展示和行为：

1. 只有当前登录用户为 `sysadmin` 时，重置密码入口可见或可用。
2. 若目标用户是 `sysadmin`，不显示重置入口，或点击时前端直接拦截提示。
3. 若目标用户是当前操作者自己，也不允许重置。

### 确认提示

点击重置密码时，确认框应明确说明：

1. 将重置为固定密码 `!b$#+^o9uF`
2. 用户下次登录必须修改密码
3. 当前登录会话会立即失效

### 成功提示

成功提示建议明确包含：

1. 目标用户名
2. 固定密码 `!b$#+^o9uF`
3. “下次登录必须修改密码”
4. “当前登录会话已失效”

因为这是后台管理员主动执行的本地管理动作，且密码为固定值，因此前端提示中可直接展示该值，不依赖接口回传。

## 与现有强制改密流程的衔接

当前系统已有基于 `must_change_password` 的强制改密链路，这次必须继续复用，不能另起一套：

1. 登录成功但 `must_change_password = 1` 时，返回现有密码修改要求。
2. 前端继续进入现有“首次登录请先修改密码”界面。
3. 用户完成改密后，后端把 `must_change_password` 改为 `0`。

这样可以避免：

- 重复 UI
- 重复接口
- 两套强制改密规则不一致

## 边界情况

1. 若目标用户不存在，返回明确错误。
2. 若目标用户已停用，仍允许重置密码；是否能登录仍由 `is_active` 决定。
3. 若目标用户当前已是 `must_change_password = 1`，再次重置时仍覆盖密码并保持 `must_change_password = 1`。
4. 若目标用户在多个设备登录，重置后所有设备会话都应失效。
5. 审计日志中不记录明文密码，只记录执行了 `RESET_PASSWORD`。

## 测试策略

### 后端单测

至少覆盖：

1. `sysadmin` 可以重置非 `sysadmin`
2. 非 `sysadmin` 不可重置任何账号
3. `sysadmin` 不可重置自己
4. `sysadmin` 不可重置 `sysadmin`
5. 重置后会更新密码 hash
6. 重置后会写入 `must_change_password = 1`
7. 重置后会调用会话吊销逻辑

### 前端测试

至少覆盖：

1. `sysadmin` 可看到重置密码入口
2. 非 `sysadmin` 不展示该入口
3. 成功提示包含固定密码与强制改密说明
4. 对 `sysadmin` 目标用户不展示或不允许执行重置

### 人工验证

建议至少验证以下流程：

1. `sysadmin` 重置 `admin` 密码成功
2. 被重置用户原有浏览器请求失效
3. 被重置用户用 `!b$#+^o9uF` 登录
4. 登录后被强制进入修改密码流程
5. 修改密码成功后恢复正常登录

## 成功标准

满足以下条件即可认为本次需求完成：

1. 只有 `sysadmin` 能重置密码。
2. `sysadmin` 只能重置非 `sysadmin` 用户。
3. 重置密码固定为 `!b$#+^o9uF`。
4. 重置后目标用户必须强制改密。
5. 重置后目标用户现有会话立即失效。
6. 全流程复用现有强制改密机制，不新增第二套密码修改流程。

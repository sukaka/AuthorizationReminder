# 多系统独立版本体系设计

## 1. 目标

将仓库从单一全局版本改为按业务系统独立版本。所有现有业务系统从 `1.0.0` 重新开始；同一业务系统内的前端、后端、网关、桌面端和部署产物共享同一版本，不同业务系统互不联动。

保留现有三段式语义版本规则和 Git 自动化闭环：

- 大改版：升级第一位并将后两位归零。
- 新功能或功能优化：升级第二位并将第三位归零。
- Bug 修复及维护类提交：升级第三位。
- 提交后自动同步版本文件、修订提交标题并推送当前分支。

## 2. 系统边界

版本系统使用显式注册表维护业务边界。首批系统如下：

| 系统 ID | 业务系统 | 主要目录 |
| --- | --- | --- |
| `auth` | 统一登录系统 | `auth/` |
| `reminder` | 授权到期提醒 | `server/`、`web/` |
| `ticketing` | 工单管理 | `ticketing/` |
| `inventory` | 库存管理 | `inventory-system/` |
| `device-flow` | 设备流转 | `device-flow/` |
| `delivery` | 交付记录 | `delivery/` |
| `sec-impl` | 聚信实施记录 | `sec-impl/` |
| `cmdb` | CMDB | `cmdb/` |
| `faq` | FAQ | `faq/` |
| `tender` | 标书系统 | `tender/` |
| `train-exam` | 培训考试 | `train-exam/` |
| `prompt-center` | 提示词管理中心 | `prompt-center/` |
| `sca` | 软件成分分析平台 | `sca-platform/` |
| `big-screen` | 统一大屏展示中心 | `big-screen-center/` |
| `ai-assistant` | 聚信 AI 助手 | `juxin-ai-assistant/` |

每个系统在注册表中定义：系统 ID、显示名称、归属路径、版本源文件、需要同步的运行时版本文件，以及允许用于共享文件提交的 scope。

新增系统必须先加入注册表并创建初始版本文件，不能依赖目录遍历自动成为版本单元。

## 3. 版本来源与同步

每个系统维护独立的 `VERSION` 文件，内容仅包含三段式版本号。所有系统迁移时统一写入 `1.0.0`。

`VERSION` 是该系统的唯一版本来源。自动化脚本根据注册表将版本同步到系统内已有的运行时文件，包括：

- `package.json` 与对应 `package-lock.json` 的根包版本。
- Tauri 的 `Cargo.toml` 与 `tauri.conf.json`。
- 前端展示常量、后端版本常量或部署脚本中的明确版本字段。
- 其他由注册表显式列出的结构化版本文件。

禁止继续扫描全仓库并替换与根版本相同的文本。版本同步只能修改被识别为受影响系统且在注册表声明过的文件。

根 `package.json` 与 `package-lock.json` 固定为版本工具自身的 `1.0.0`，不再代表整个平台，也不参与业务提交升版。

## 4. 受影响系统识别

提交前后通过 Git 的变更文件列表识别受影响系统：

1. 业务目录文件按照注册表中的路径归属自动映射到系统。
2. 一次提交修改多个系统目录时，所有命中的系统都参与本次升版。
3. 根级共享文件、统一部署文件和跨系统基础设施文件不能仅靠路径判断，必须由 commit scope 指定目标。
4. `all` scope 表示确实影响全部系统，所有系统按本次提交类型升级。
5. scope 指定的系统与实际业务路径不一致时阻止提交，并输出冲突路径与期望 scope。
6. 仅修改版本自动化、仓库工具或独立文档且不影响业务系统时，使用 `repo` scope，不升级业务系统。

共享文件清单由注册表或独立配置显式维护，至少覆盖根 `docker-compose*.yml`、统一部署脚本、根入口文档及跨系统网关配置。

## 5. 提交与升版规则

提交类型沿用现有规则：

- `breaking:`、`major:`、Conventional Commit 的 `!`：主版本升级。
- `feat:`、`minor:`、`perf:`：次版本升级。
- `fix:`、`patch:`、`docs:`、`chore:`、`style:`、`refactor:`、`test:`、`build:`、`ci:`、`revert:`：修订号升级。
- `Merge`、`fixup!`、`squash!`：不自动升级。

同一次提交涉及多个系统时，所有受影响系统使用同一个升级级别，但各自基于当前版本独立计算下一版本。

示例：

- `feat(inventory): 增加库存批量导入`：库存系统 `1.0.0 -> 1.1.0`。
- `fix(auth): 修复登录超时`：登录系统 `1.0.0 -> 1.0.1`。
- 同时修改登录和库存目录的 `feat:`：登录与库存分别升级，其他系统不变。
- `feat(all): 更新所有系统公共入口协议`：所有系统次版本升级。

自动修订后的提交标题格式为：

- 单系统：`[inventory-v1.1.0] feat(inventory): 增加库存批量导入`
- 多系统：`[auth-v1.1.0][inventory-v1.1.0] feat: 联动优化登录与库存`
- 仓库工具：`[repo] chore(repo): 调整版本自动化测试`

版本前缀按系统 ID 排序，确保同一提交的标题稳定且可测试。

## 6. Git 分支与推送

仓库不再存在唯一全局版本，因此取消根据版本自动切换 `codex/<版本号>` 分支的逻辑。系统版本变化不能决定整个仓库的分支名称。

保留以下行为：

- `commit-msg` 校验提交类型、scope 和路径归属。
- `post-commit` 计算受影响系统版本并同步文件。
- 自动使用 `git commit --amend` 将版本文件与标题并入原提交。
- 自动推送当前分支；没有 upstream 时自动建立 upstream。
- 使用旁路环境变量时跳过自动修订，供版本脚本自身提交、合并恢复和紧急维护使用。

不自动创建系统级 Git tag。后续如需要发布标签，应采用带系统 ID 的标签，例如 `inventory-v1.2.0`，避免不同系统的 `v1.2.0` 冲突。

## 7. 错误处理

以下情况必须阻止提交或自动修订：

- 未知 scope。
- 修改共享文件但没有系统 scope、`all` 或 `repo` scope。
- scope 与业务路径映射冲突。
- 系统 `VERSION` 缺失或不是三段式版本。
- 注册表中两个系统声明了重叠业务路径。
- 同步目标文件内容不合法或结构不符合预期。
- 自动 amend 或推送失败。

失败输出必须包含具体系统、文件和恢复建议。自动化不得删除、重置或覆盖未提交的用户改动；继续沿用暂存和恢复机制保护工作区。

## 8. 迁移方案

迁移在一个受控提交中完成：

1. 创建系统注册表和每个系统的 `VERSION`。
2. 将全部系统版本及其运行时版本同步为 `1.0.0`。
3. 将根版本工具包重置为 `1.0.0`。
4. 替换全局扫描和根版本读取逻辑。
5. 取消版本驱动的自动分支切换。
6. 更新 Git Hook 校验、提交标题格式、文档和测试。
7. 使用版本旁路提交迁移本身，避免旧钩子在迁移提交期间执行全局升版。
8. 推送当前业务分支，不删除历史全局版本分支和标签。

历史提交、历史标签和历史发布文档保持原样，用作审计与回滚依据。

## 9. 测试与验收

自动化测试至少覆盖：

- 每个系统初始版本均为 `1.0.0`。
- 单系统 `major/minor/patch` 升版。
- 同系统前端、后端、网关同步一致。
- 多系统提交分别升级且不影响其他系统。
- 共享文件 scope、`all`、`repo` 的合法路径。
- scope 与路径冲突时提交失败。
- 未知系统、重叠路径、非法版本和缺失版本文件失败。
- 提交标题的单系统、多系统和稳定排序格式。
- 自动 amend 保留原提交内容。
- 当前分支自动推送，不再切换到全局版本分支。
- 未跟踪及未提交文件在自动化前后保持不变。

验收时运行版本自动化测试、JSON/配置结构校验，并抽查所有系统的版本源与运行时版本是否一致。

## 10. 非目标

- 不为每个系统拆分独立 Git 仓库。
- 不改变现有前端、后端和网关的部署拓扑。
- 不在本次引入独立发布流水线或系统级自动打 tag。
- 不修改历史提交、历史标签或历史发布记录。

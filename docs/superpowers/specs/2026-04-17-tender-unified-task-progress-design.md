# 标书系统统一长任务进度可视化设计

## 背景

当前标书协同制作系统的多个长任务已经在后端落有任务表，但前端等待态仍以“已等待多久”为主，展示的是按时间推导的假进度，而不是任务真实进展。直接结果是：

1. 用户看到“分析中”“请继续等待”，但不知道当前在做什么。
2. 刷新页面、重新进入项目后，等待界面无法稳定恢复到真实任务状态。
3. 不同用户接手同一项目时，无法直接看见当前任务跑到哪一步。
4. 各类长任务的等待交互各自为政，后续越来越难维护。

这次需求不是只优化“开始分析”一处提示，而是为标书系统的长任务建立统一、可恢复、可复用的进度可视化能力。

## 目标

第一期完成以下目标：

1. 统一标书系统长任务的状态表达方式，不再依赖前端本地计时假装进度。
2. 用户刷新页面、重新进入项目时，仍能看到当前任务跑到哪一步。
3. 换人接手同一项目时，只要有权限，也能看到同一份任务状态。
4. 页面中统一展示：
   - 当前阶段
   - 百分比
   - 开始时间
   - 最近更新时间
   - 操作人
   - 最近 5 条执行日志
5. 失败时直接展示最后阶段和错误信息，不再只显示笼统失败提示。

## 非目标

1. 第一期不引入 WebSocket 或 SSE，先使用统一轮询。
2. 第一期不做任务取消、手动重试、批量管理能力。
3. 第一期不建设独立“任务中心”页面，先优先解决项目内等待态不可见的问题。
4. 第一期不记录大段模型原始输出，仅记录面向用户可读的轻量执行日志。

## 方案对比

### 方案 A：仅补当前页面文案

做法：继续保留各页面自己的等待态，只把“分析中”之类的文案改得更具体。

优点：改动最小，交付快。

缺点：

- 仍然是前端本地推导，不是真实任务状态。
- 刷新后难以恢复。
- 不同任务类型继续各写各的，无法统一。

### 方案 B：统一任务状态模型 + 统一任务状态卡

做法：在现有任务表基础上补统一阶段字段和事件日志，前端抽一套统一任务状态卡，在解析、分析、生成、导出等场景复用。

优点：

- 能满足“刷新恢复”“重新进入恢复”“换人接手可见”。
- 结构统一，后续扩展新任务类型成本低。
- 第一期开销可控，不需要大改系统架构。

缺点：

- 需要补后端字段、接口聚合和前端公共组件，不是纯前端小修。

### 方案 C：统一任务模型 + 独立任务中心

做法：在方案 B 基础上，再单独增加任务中心页面，集中查看全部长任务。

优点：完整度最高。

缺点：

- 超出这次需求的最小闭环。
- 会拉长第一期交付时间。

## 结论

采用方案 B：先建立统一任务状态模型与统一任务状态卡，在项目内各长任务入口就地展示。独立任务中心放到后续迭代。

## 第一期开启范围

第一期覆盖以下长任务：

1. 解析工作台中的解析任务
2. 生成向导中的分析任务
3. 初稿生成 / 自动填充相关任务
4. 导出任务

如 OCR、知识库沉淀等链路已经具备明确任务实体，也按同一模型兼容；如果当前实现仍偏同步或没有稳定任务主表，则暂不强行纳入第一期主路径。

## 统一任务模型

### 设计原则

1. 尽量复用现有任务表，不新建一套与现有表并行的“大任务总表”。
2. 用统一接口形状屏蔽后端底层表差异。
3. 阶段文案以“用户可理解”为原则，不暴露内部实现细节或模型原始返回。

### 统一任务字段

每个长任务在接口层都整理为统一结构：

- `task_type`：任务类型，如 `PARSE`、`ANALYZE`、`GENERATE_DRAFT`、`EXPORT`
- `task_id`：原任务主键
- `related_bid_id`：所属项目 ID
- `status`：`PENDING` / `RUNNING` / `SUCCESS` / `FAILED`
- `progress`：0-100
- `stage_key`：稳定枚举，用于前端映射样式与兜底文案
- `stage_text`：用户当前看到的阶段标题
- `detail_text`：阶段说明，例如“已完成 3/8 个文件，正在处理商务文件”
- `started_at`
- `updated_at`
- `operator_id`
- `operator_name`
- `summary`：任务完成后的简要结果摘要，失败时可为空

### 统一阶段枚举约定

不同任务有不同阶段，但风格保持一致。示例：

- 解析任务：
  - `PREPARE_INPUT`
  - `PARSE_STRUCTURE`
  - `EXTRACT_TABLES`
  - `MATCH_REQUIREMENTS`
  - `BUILD_SUMMARY`
- 分析任务：
  - `LOAD_SOURCE`
  - `SPLIT_SECTIONS`
  - `EXTRACT_SCORE_ITEMS`
  - `IDENTIFY_RISKS`
  - `BUILD_ANALYSIS_RESULT`
- 初稿生成任务：
  - `LOAD_CONTEXT`
  - `SELECT_SAMPLES`
  - `GENERATE_SECTIONS`
  - `FILL_ARTIFACTS`
  - `BUILD_DRAFT`
- 导出任务：
  - `LOAD_TEMPLATE`
  - `MERGE_CONTENT`
  - `RENDER_DOCUMENT`
  - `UPLOAD_EXPORT`
  - `FINALIZE_EXPORT`

要求：

1. `stage_key` 稳定，便于测试和前端复用。
2. `stage_text` 可按任务类型直接返回，不强制前端自己拼。
3. `detail_text` 可为空，但只要后端有上下文，就优先给出更具体的描述。

## 任务事件日志

### 新增日志表

新增轻量任务事件表 `tender_task_events`，用于承载可恢复的执行日志。

建议字段：

- `id`
- `task_type`
- `task_id`
- `bid_id`
- `event_type`：如 `INFO`、`STAGE_CHANGED`、`WARNING`、`ERROR`
- `message`
- `progress`
- `operator_id`
- `operator_name`
- `created_at`

### 日志写入原则

1. 只记录用户可读、可展示的轻量文本。
2. 阶段切换时至少写一条日志。
3. 失败时至少写入一条错误日志。
4. 默认前端展示最近 5 条，后端可保留更多历史。
5. 不在日志中写入大段原始模型响应、密钥、路径等敏感实现细节。

示例日志：

- `已开始解析，共 9 个文件`
- `已提取章节结构，正在识别评分项`
- `已完成 18 条评分项归并`
- `文档导出完成，正在上传结果文件`
- `导出失败：模板文件缺失`

## 后端落地方式

### 复用现有任务主表

优先复用现有任务表：

- `tender_bid_parse_jobs`
- `tender_bid_generate_jobs`
- `tender_bid_export_records`

需要补充或统一的字段包括：

- `stage_key`
- `stage_text`
- `detail_text`
- `started_at`（如现有 `created_at` 已能表达启动时间，可直接映射）

如果某些表已经有 `status`、`progress`、`operator_*`、`updated_at`，则继续沿用，不重复造字段。

### 统一读取接口

提供两类读取接口：

1. 项目维度任务概览  
   用于项目详情页、生成向导、导出区块恢复任务态。
   返回：
   - 当前项目最近活跃任务
   - 最近若干已完成/失败任务
   - 每个任务的最近 5 条日志

2. 单任务详情  
   用于某些页面已知任务 ID 时轮询刷新。
   返回：
   - 当前任务完整状态
   - 最近日志

统一接口层负责把不同底层表归一为同一输出结构，前端不直接感知具体表差异。

### 状态推进规则

1. 任务启动时写入：
   - `status=RUNNING`
   - `progress` 初始值
   - 第一条日志
2. 阶段推进时同步更新：
   - `stage_key`
   - `stage_text`
   - `detail_text`
   - `progress`
   - 新日志
3. 成功时写入：
   - `status=SUCCESS`
   - `progress=100`
   - 完成摘要
4. 失败时写入：
   - `status=FAILED`
   - 错误日志
   - 最后阶段与错误说明

## 前端统一交互

### 统一任务状态卡

新增统一任务状态卡组件，在不同长任务入口复用，而不是继续每个场景各写一套 loading 区块。

卡片固定展示：

1. 当前阶段
2. 百分比和进度条
3. 开始时间
4. 最近更新时间
5. 操作人
6. 最近 5 条日志

### 展示位置

采取“就地展示”原则：

- 分析任务卡显示在生成向导分析按钮下方
- 解析任务卡显示在解析工作台核心操作区
- 初稿生成任务卡显示在生成/自动填充操作区
- 导出任务卡显示在导出区域

用户不需要跳转到别处查看任务进展。

### 恢复规则

1. 页面进入项目详情时，主动请求该项目最近活跃任务。
2. 若存在 `RUNNING` 或 `PENDING` 任务，则直接恢复对应任务卡。
3. 若任务已 `SUCCESS` 或 `FAILED`，则展示结果态卡片一段时间，不立即消失。
4. 刷新页面、重新进入项目、不同用户重新打开同一项目时，看到的是同一份后端任务状态。

### 多任务并存策略

一个项目可能同时存在多个长任务。第一期策略：

1. 优先展示“最近启动且仍在运行”的任务作为主任务卡。
2. 其他最近任务可在主卡下方以简版列表展示。
3. 不在第一期引入复杂任务编排 UI。

### 轮询策略

第一期采用统一轮询：

1. 当页面存在活跃任务卡时，每 2-3 秒刷新一次。
2. 成功或失败后停止高频轮询，转为静态展示结果。
3. 离开当前项目或关闭弹层时，清理轮询。

## 失败态与异常边界

1. 若任务长时间无更新，不显示“卡死”，而显示“执行时间较长，最近更新时间 xx:xx”。
2. 若后端暂时拿不到细粒度阶段，允许回退到通用阶段文案，但仍展示真实更新时间、操作人和日志。
3. 若不同用户接手项目，任务卡需要明确显示实际触发人。
4. 若任务失败，直接展示失败阶段、错误说明和最后几条日志。
5. 若接口短时读取失败，不覆盖已有任务卡内容，避免界面闪回到空白状态。

## 与现有实现的衔接

当前前端生成向导中的运行态文案由前端根据等待时间推导，例如“正在解析章节与表格”“正在提取得分项与风险项”。这类时间驱动的假进度在统一方案落地后应退居兜底，不再作为主显示来源。

原则上：

1. 优先展示后端返回的真实阶段与日志。
2. 只有在历史任务数据尚未补齐的过渡期，才回退到现有时间推导文案。
3. 过渡期结束后，主流程等待态统一切换为真实任务状态卡。

## 测试策略

### 后端

1. 任务阶段推进测试：验证任务状态、阶段、进度和日志同步更新。
2. 失败态测试：验证失败时最后阶段、错误日志和错误消息可回读。
3. 项目维度读取测试：验证按项目能正确聚合最近活跃任务和最近日志。

### 前端

1. 统一任务卡渲染测试：验证阶段、进度、时间、操作者、日志正确展示。
2. 恢复逻辑测试：验证刷新后能从项目维度接口恢复活跃任务。
3. 多任务选择测试：验证优先显示最近活跃任务。

### 手工验证

至少覆盖以下链路：

1. 启动分析后刷新页面，任务卡恢复。
2. 离开项目后重新进入，任务卡恢复。
3. 更换账号后进入同一项目，能看到当前任务状态与操作者。
4. 人为制造失败，页面显示失败阶段和最近错误日志。

## 实施顺序建议

1. 先补统一任务字段与任务事件表。
2. 再补项目维度/任务维度读取接口。
3. 然后前端抽统一任务状态卡并接入生成向导。
4. 再接入解析、初稿生成、导出区域。
5. 最后删除主流程中依赖本地计时的假进度主显示。

## 风险与控制

### 风险 1：不同任务表结构不完全一致

控制方式：统一在接口层做归一，不要求底层任务表一步到位完全相同。

### 风险 2：日志写入过多导致噪音或膨胀

控制方式：只写阶段变化和关键里程碑，不记录细碎内部调试信息。

### 风险 3：前端切换过程中出现新旧等待态并存

控制方式：以统一任务状态卡为主显示，现有时间推导等待态只作过渡兜底，并在实现后逐步移除。

## 成功标准

满足以下条件即可认为第一期达成：

1. 解析、分析、初稿生成、导出四类长任务均可显示真实阶段。
2. 页面刷新、重新进入项目、换人接手时，任务状态可恢复。
3. 用户可以看到当前阶段、百分比、开始时间、最近更新时间、操作人、最近 5 条日志。
4. 失败态可见且信息可理解。
5. 主流程不再以纯等待时间推导的假进度作为唯一反馈。

# 设备流转单用户可见范围设计

## 背景

设备流转系统当前只校验用户是否已登录，流转单列表和详情接口没有数据范围限制。因此任意已登录用户都能查看全部流转单及其关联信息，不符合按创建人和二次复签人隔离数据的要求。

## 目标

1. 只有角色严格为 `admin` 的用户可以查看全部流转单。
2. 其他角色只能查看自己创建的流转单。
3. 被指定为二次复签人的用户可以查看对应流转单，并永久保留查看权限。
4. 数据隔离在后端执行，不能依赖前端隐藏。
5. 无权访问具体流转单时返回 404，避免泄露单据是否存在。

## 非目标

1. 不调整现有菜单权限、操作权限或阶段权限的配置方式。
2. 不新增流转单人工共享、部门共享或临时授权功能。
3. 不改变二次复签的发起、完成、过期和签名校验流程。
4. 不把 `sysadmin` 视为全量数据管理员；其数据范围与其他非 `admin` 用户相同。

## 方案对比

### 方案 A：后端统一数据范围过滤

列表查询使用统一 SQL 可见条件，单据详情及关联资源接口使用同一规则校验。

优点：数据边界可靠，改动集中，直接复用现有创建人和双签记录。

缺点：需要梳理所有按流转单 ID 读取或操作的接口。

### 方案 B：新增流转单可见用户授权表

在创建和指定复签人时写入独立授权记录。

优点：以后扩展人工共享和部门授权更方便。

缺点：当前需求只有两类可见来源，新增表、历史数据回填和同步逻辑过重。

### 方案 C：仅过滤前端列表

优点：改动最小。

缺点：用户仍可通过接口或已知 ID 查看他人数据，不能形成安全边界。

## 结论

采用方案 A。

## 可见性规则

流转单对当前用户可见，当且仅当满足以下任一条件：

1. 当前用户角色为 `admin`。
2. `device_jobs.created_by_sub` 等于当前用户 ID。
3. 该流转单在 `device_dual_sign_sessions` 中存在记录，且 `expected_second_signer_sub` 或 `second_signer_sub` 等于当前用户 ID。

双签记录的状态不参与可见性判断。用户一旦被指定为第二复签人，即使会签已完成、已过期或后续重新发起，仍永久保留该流转单的查看权限。

## 后端设计

1. 提供统一的流转单数据范围 SQL 构造逻辑，列表总数和列表数据必须使用完全相同的条件。
2. 提供统一的单据访问断言，用于按 ID 读取详情及访问附件、锁、推进、退回、变更申请和标签等关联接口。
3. `admin` 不附加数据范围条件；所有其他角色都附加创建人或二次复签人的可见条件。
4. 无权访问时与不存在统一返回 404，错误文案为“流转单不存在或无权访问”。
5. 前端继续消费现有列表和详情接口，不复制权限判断。

## 数据流

1. 用户登录后，认证中间件提供用户 ID 和角色。
2. 列表请求根据角色生成数据范围条件，再叠加关键词和阶段筛选。
3. 单据详情或关联操作先按同一可见规则读取流转单。
4. 通过校验后继续执行现有业务逻辑；未通过则立即返回 404。
5. 创建二次复签会话后，指定复签人从下一次请求开始获得该流转单的永久查看权限。

## 测试策略

1. `admin` 查询不附加数据范围限制。
2. 创建人可以查看自己的流转单。
3. 指定的第二复签人可以查看对应流转单，包括已完成或已过期的双签记录。
4. `sysadmin` 和普通用户不能查看既非自己创建、也未被指定复签的流转单。
5. 列表总数、列表数据和单据详情使用一致的可见性规则。
6. 运行设备流转后端测试、语法检查和前端构建，随后重建设备流转容器并检查健康状态。

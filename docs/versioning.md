# 系统版本规范

本文档定义整套系统的统一版本号规则。后续发布、分支命名、标签命名、发布说明都按本规范执行。

## 1. 标准格式

- 统一格式：`主版本.次版本.修订号`
- 示例：`4.1.2`

## 2. 三段含义

- `主版本`
  - 表示大改版
  - 适用于架构升级、产品形态明显变化、独立系统拆分、权限模型或部署方式发生明显变化
- `次版本`
  - 表示功能优化
  - 适用于新增功能、功能增强、流程优化、页面重做、兼容性增强，但不属于整套系统重构
- `修订号`
  - 表示 Bug 修复
  - 适用于缺陷修复、安全补丁、配置修正、构建与部署问题修复、文档勘误

## 3. 升级规则

### 3.1 升主版本

满足任一条件时，升级第一位：

- 多个系统的核心入口、信息架构或整体交互方式发生重构
- 关键部署模式、鉴权模型、数据模型存在明显不兼容变化
- 产品从“单系统增强”演进为“平台级改版”

升级示例：

- `4.3.7` -> `5.0.0`

### 3.2 升次版本

满足任一条件时，升级第二位，第三位归零：

- 新增独立系统或新模块
- 现有系统增加重要业务能力
- 页面或流程存在可感知的功能优化，但不构成大改版

升级示例：

- `4.0.9` -> `4.1.0`
- `4.2.5` -> `4.3.0`

### 3.3 升修订号

满足任一条件时，升级第三位：

- 修复线上缺陷
- 修复构建、部署、兼容性问题
- 修复安全问题或配置错误
- 修正文档和发布材料中的错误

升级示例：

- `4.1.0` -> `4.1.1`

## 4. 当前口径

- 当前整套系统口径版本：`4.1.2`
- 后续如果做整套后台/门户的大改版，下一次应评估是否进入 `5.0.0`
- 如果只是持续增强当前版本线中的功能，优先升级 `次版本`
- 如果只是修缺陷，优先升级 `修订号`

## 5. 仓库约定

### 5.1 Git 分支

- 版本开发分支使用：`codex/<主版本>.<次版本>.<修订号>`
- 示例：`codex/4.1.2`

### 5.2 Git 标签

- 发布标签使用：`v<主版本>.<次版本>.<修订号>`
- 示例：`v4.1.2`

### 5.3 发布文档

- 发布说明文件放在：`docs/releases/`
- 文件名统一使用：`<主版本>.<次版本>.<修订号>.md`
- 示例：`docs/releases/4.1.2.md`

## 6. 判定优先级

当一次发布同时包含多类变更时，按影响级别最高的那一类决定版本号：

- 大改版优先于功能优化
- 功能优化优先于 Bug 修复

例如：

- 同时包含“独立后台拆分”和“若干修复”时，应按大改版处理
- 同时包含“新增用户导入”和“若干修复”时，应按功能优化处理

## 7. 执行要求

- 每次准备发布前，先判断本次变更属于哪一类
- 先确定版本号，再创建发布说明、分支和标签
- 不允许只改标签不更新发布文档
- 不建议多个子系统各自维护不同的对外版本口径；对外统一以整套系统版本为准
